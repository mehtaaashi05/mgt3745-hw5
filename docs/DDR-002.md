## 4. Trust Boundary

**Crossed to:** GitHub and the model provider, plus the deployed Cloudflare Worker endpoint. The app still talks only to my own Worker and D1 database.

**Accountable:** me. I reviewed the generated code, retained responsibility for the final repo state, and documented any residual uncertainty.

**Reverse crossing:** no new packages or runtime dependencies were introduced by the Copilot-assisted wiring. The only external call in the app is the fetch to the Worker URL.

**Limit I could not verify:** whether Cloudflare infrastructure logs retain client IP metadata. I addressed that by keeping entries fictional and documenting the boundary in [context/ARCHITECTURE.md](../context/ARCHITECTURE.md).

## 5. Verification performed

**Code eval:** `evals/worker.test.js`, run with `API=<worker url> npm test`. Tests included:

- "EARS: THE SYSTEM SHALL return all entries in creation order (GET /entries is 200 + array)"
- "EARS: IF the entry text is missing, THEN THE SYSTEM SHALL reject it (POST {} is 400)"
- "EARS: WHEN a valid entry is submitted, THE SYSTEM SHALL store it (POST then GET shows it)"

Result: 3 of 3 tests passed.

**By hand against the deployed Worker:**
- POST with empty text returned 400 and "text required"
- POST with more than 200 characters returned 400 and "text must be 200 characters or fewer"
- DELETE with an invalid ID returned 400
- DELETE against a missing ID returned 404

**By reading the code:**
- Every INSERT and DELETE in [worker.js](../worker.js) uses `bind()`; the SELECT uses a fixed query without concatenated user input.
- [app.js](../app.js) renders page text with `textContent` rather than `innerHTML`.
- Each fetch checks `response.ok` before updating the UI.

**Judgment eval:** the repo’s rubric questions on error display and safe rendering were checked in the judgment record.

## 6. Findings

Pass count: 3 of 3 code-eval tests; all manual Worker checks matched the expected behavior.

**From reading the code this week:**
- `refresh()` in [app.js](../app.js) catches fetch failures and surfaces a page-level error, which is the correct user-facing fallback for the Worker being unavailable.
- `saveEntry()` returns the worker response text to the user, which is acceptable here because the content is fictional and the Worker does not expose a private secret.
- CORS in [worker.js](../worker.js) is intentionally limited to the Live Server origin, which matches the assignment’s static page deployment pattern.

**From the checks above:**
- The Worker accepted valid entries and returned them via the next `GET /entries`, proving the page-to-API flow works.
- The invalid input paths all failed with the expected 400 responses, which is what the app is supposed to show to a user.

**Could not fully verify:** Cloudflare’s platform-level request logging and the exact retention policy for client metadata. I addressed that by documenting the trust boundary and keeping the directory data fictional.
